# Agent Note: Releases people can download

Status: implemented — a tag builds the desktop app as system packages for current Ubuntu, Fedora and Arch, attached to a GitHub release; the README leads with the download

## Problem

Installing from source is a developer's way: clone the repository, install uv, and
install from the checkout on the command line. Someone who wants to try the app turns away
at the first step without a download on GitHub.

Briefcase builds the app as a package
([the desktop app note](2026-11-07-desktop-app.md)), and
`packaging/build-linux.sh` builds one for the machine it runs on; something has to build
them for others and put them where people look.

## Decision

### A tag makes a release

- Pushing a tag `v<version>` runs `.github/workflows/release.yml` on GitHub's Ubuntu
  runners. It checks the tag against the version in `pyproject.toml` (`[project]` and
  `[tool.briefcase]` carry the same one), builds, and creates the GitHub release with the
  files and the version's section of `CHANGELOG`.
- What it builds: Briefcase's system packages, each in a Docker image of its system, each
  installed with the system's own installer, which also brings what Qt needs from the
  system (`system_runtime_requires`):
  - a **.deb** for Ubuntu 24.04 and one for 26.04;
  - an **.rpm** for Fedora 44 (not 45: its Python 3.15 has no build of sherpa-onnx,
    the speech library, yet);
  - an **Arch package** (`.pkg.tar.zst`).
  A system package runs on its system's own Python, with Kaden's libraries built for that
  Python: one package per release, not one for "24.04 or newer". Each adds `kaden` and
  `kd` beside `kaden-desktop`, as `packaging/build-linux.sh` does for a local build.
- Before the release, each package is installed with its system's installer in a fresh
  image of that system and started (`packaging/try-linux.sh`): `kaden --help` answers,
  and the desktop app, drawn off screen, is still running after 30 s.
- Run by hand, the workflow only builds (its packages are the run's artifacts), to try a
  change before a tag.
- The GPU voice (PyTorch) is not packaged: several GB for a few users. The packages have
  the normal voice; the GPU voice stays an install from source.

### The README leads with the download

"Download" first: which package of the latest release fits which system, how to install
it, and that the app asks for a provider's key on first start. Installing from source
moves to Getting started, for other systems, the GPU voice and contributors.

### Outside it

- **PyPI and Homebrew:** [Homebrew and PyPI](../proposed/2026-11-27-homebrew-and-pypi.md).
- **macOS and Windows:** [macOS, the rest](../proposed/2026-11-25-macos-the-rest.md) and

- **Flathub, AUR:** not published.

## Alternatives considered

- **An AppImage**, one file for any Linux, downloaded and run. Briefcase warns against
  it: in its words, AppImage "has proven to be highly unreliable as a distribution
  platform", cannot use pre-compiled wheels and has significant problems with PySide;
  its local build also failed in Briefcase's own template. Building one with other tools
  would be a packaging pipeline of Kaden's own.
- **Flatpak as the main download.** Flatpak sandboxes the
  app: the agent's shell would run inside the sandbox, not on the user's computer, unless
  every command goes through `flatpak-spawn --host`, which needs a permission that
  defeats the sandbox. Kaden's purpose is to work on the user's computer. Ubuntu also
  ships without Flatpak.
- **PyPI only.** One line, but it needs uv or pipx first: still a terminal install.
- **An install script** (`curl … | sh`). Common, but asks people to run a script from the
  web in a terminal, which is what this note is meant to spare them.
- **PyInstaller instead of Briefcase.** Briefcase already builds Kaden and makes the
  system packages too.

## Consequences

- A release needs nothing run on the maintainer's machine; a tag that does not match the
  version fails before building, and a package that does not install and start on a fresh
  system stops the release.
- Only the releases built for are covered: other distributions, and releases whose
  Python differs, install from source. Arch moves to a new Python before a release is
  rebuilt; until then its package does not start.
- What a system must provide is listed by hand from Qt's requirements; a missing one shows
  only on a system without it.
- Unsigned downloads: browsers and systems may warn.
- The keychain needs a Secret Service (GNOME Keyring, KWallet); without one the app says
  so when saving a key.
- Each package is large: about 190 MB to download and 630 MB installed (Qt and Kaden's
  libraries).
