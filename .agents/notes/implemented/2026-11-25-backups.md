# Agent Note: Backups

Status: implemented — the desktop app keeps daily backups of Kaden's data folder, the user's chats and Continuous alike, thinned to 7 daily, 4 weekly and 6 monthly

## Problem

Everything a person has with Kaden is in its data folder: their chats (the archive and the
memory folders), and Continuous, whose life is its whole identity (its one conversation,
its memory files, its journal, its home). One damaged database, a mistaken deletion or a
careless move of the folder loses it for good. Moving the life's folder by hand already
cost it its memory index once (2026-11-23). There is no backup of any of it.

## Decision

- **What:** the data folder (`~/.kaden`), the life's folder in it included, except what
  can be had again: the speech models and the prepared voice recordings (`voice/`, 5.6
  GB), the backups themselves, and the instance lock. A database (any `*.db`) is copied
  with SQLite's online backup (`sqlite3.Connection.backup`), so the copy is whole and
  consistent while Kaden, or the life's process, writes to it; its `-wal` and `-shm`
  files are not copied, as the copy has none to go with. Every other file is copied as
  it is. About 11 MB, copied in 0.03 s (2026-11-25).
- **When:** the desktop app makes one when it starts unless one was made today, and checks
  every hour while it runs, so a day it runs gets one. In the background, off the event
  loop.
- **Where:** `~/.kaden/backups/<yyyy-mm-dd>/`, plain folders laid out as the data folder.
  A backup is written under a temporary name and renamed when whole, so a folder with a
  date is a complete backup.
- **How many:** after each backup, the folder is thinned as restic's `--keep-daily 7
  --keep-weekly 4 --keep-monthly 6` does (grandfather-father-son): the newest backup of
  each of the last 7 days that have one, of each of the last 4 weeks, and of each of the
  last 6 months; one backup may count for more than one of these. The rest are deleted.
  About 17 backups, reaching back half a year.
- **Restoring:** by hand, described in the docs (Using Kaden, Backups): quit Kaden, then
  put the backup's files back, removing the `-wal` and `-shm` files beside each database
  put back.
- **A failure** is said once as a notice in the conversation on screen, until a backup
  succeeds again.
- **Shared code:** `runtime/backup.py` copies a data folder and thins backups; it reads no
  module's format and knows only "a database is a `*.db` file". The desktop app, which is
  what runs day to day, starts it (`backup.keep_backed_up`).

## Alternatives considered

- **30 daily backups.** Simpler, but reaches back only a month with nearly twice the
  copies; the user asked for the usual standard, which is the thinned one.
- **Only Continuous.** Its life is its identity, but the user's chats are as irreplaceable,
  and both are small.
- **Copying the database files as they are.** Simple, but a copy taken while the database
  is written can be torn; SQLite's backup is made for this.
- **A backup tool (restic, Borg).** Deduplicated and with off-site targets, but another
  program to install and run for 6 MB of data.
- **Backups in the runtime, for every instance.** Headless instances (KFM's units, sub-
  sessions) would back themselves up too, which nobody asked for; their data folders are
  the fleet's or the parent's to keep.

## Consequences

- A day the app runs leaves a complete backup of the chats and the life, consistent while
  both run (checked on the user's data: every database whole, with what was still in its
  `-wal` file); about 17 backups, near 190 MB at today's size.
- The backups are on the same disk: they do not survive the disk dying or the computer
  being lost (the 3-2-1 rule wants a copy elsewhere). Copying the backups folder
  elsewhere is left to the user, as the docs say.
- Restoring is by hand and can go wrong: a stale `-wal` file applied to a restored
  database damages it, so the docs say to remove them.
- Only the desktop app backs up: a data folder used only headless or from the terminal
  has none.
